# Real-World Java Projects

Projects are where separate concepts become a working system. Build them incrementally and do not introduce tools before the learner understands why they are needed.

## Project progression

| Stage | Project | Concepts demonstrated |
|---|---|---|
| 01 | Console Calculator | Input, validation, methods, conditions and loops |
| 02 | Number Guessing Game | Randomness, loops, control flow and input handling |
| 03 | Bank Account Simulator | Classes, objects, encapsulation, invariants and exceptions |
| 04 | Student Grade Manager | Collections, sorting, searching and validation |
| 05 | Library Management System | OOP, collections, interfaces, exceptions and file persistence |
| 06 | Inventory Management Application | Layered design, JDBC, SQL, transactions and testing |
| 07 | Concurrent Ticket Booking Simulation | Shared state, race conditions, synchronization and executors |
| 08 | Expense Management Backend | REST API, persistence, validation, tests and maintainable architecture |

## Required project documentation

Every substantial project should include:

1. Problem statement and intended users
2. Scope: what is included and explicitly excluded
3. Functional requirements
4. Non-functional requirements
5. Domain model and key invariants
6. Architecture and package structure
7. Data model and persistence decisions, if applicable
8. Implementation milestones
9. How to build and run
10. Example requests, outputs or screenshots
11. Tests and test strategy
12. Error handling and security considerations
13. Known limitations
14. Future improvements
15. Interview walkthrough: explain the design and trade-offs

## Engineering review questions

After completing a project, ask:

- What problem does this application solve?
- Why is the code divided into these classes or layers?
- Where is input validated?
- What happens when an operation fails?
- What assumptions does the design make?
- What could go wrong with concurrent users?
- How would you test the most important behaviour?
- What would need to change before production use?

A project is not production-ready just because it runs on a developer's machine. Document limitations honestly.
